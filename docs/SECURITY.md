# امنیت — SadGallery

> این سند زنده است: در پایان هر فاز، وضعیت هر کنترل واقعی به‌روزرسانی می‌شود. **هیچ‌گاه امنیت صددرصدی تضمین نمی‌شود؛** در این سند فقط کنترل‌های اجراشده و ریسک‌های باقی‌مانده ثبت می‌شوند.

## ۴. رمزنگاری و عبارت محرمانه (مهم‌ترین بخش این سند)

### ۴.۱ تصمیم پایه
عبارت محرمانه (Passphrase) **هرگز** مستقیماً کلید رمزنگاری نیست و هرگز در کد، Git، لاگ یا پیام خطا ظاهر نمی‌شود. از آن فقط برای **مشتق‌سازی کلید** با KDF استاندارد استفاده می‌شود. جزئیات تصمیم: `DECISIONS/ADR-0006`.

### ۴.۲ معماری کلید (دو لایه، نسخه‌بندی‌شده)

```
Passphrase (از Secret Store)
     │  PBKDF2-HMAC-SHA256 (Salt تصادفی ۱۶ بایت، Iterations قابل‌تنظیم، نسل نسخه)
     ▼
MasterKey  (۳۲ بایت، نسخه‌دار: KeyVersion = 1)
     │  HKDF-SHA256 با info اختصاصی هر کاربرد
     ├─ info="SadGallery.SecretStore.v1"    → Key_SecretStore   (رمزنگاری رازهای DB: API Key پیامک/نرخ)
     ├─ info="SadGallery.Pii.v1"            → Key_Pii           (اطلاعات هویتی مثل NationalId)
     ├─ info="SadGallery.OtpHmac.v1"        → Key_OtpHmac       (HMAC برای هش کد یک‌بارمصرف)
     └─ info="SadGallery.IdentifierHmac.v1" → Key_IdentifierHmac (هش شناسه ورود/آی‌پی در Audit)
```

**قواعد سخت:**
1. **هیچ کلیدی با کاربردی دیگر به اشتراک گذاشته نمی‌شود** (تقسیم کلید با HKDF + برچسب `info` مستقل).
2. **AES-256-GCM** برای همه داده‌های قابل بازیابی؛ هر رکورد Nonce یکتای ۱۲ بایتی (CSPRNG) + Tag ۱۶ بایتی.
3. **قالب داده نسخه‌بندی‌شده** برای هر رکورد رمزنگاری‌شده:
   `v1 | KeyId(2B) | Nonce(12B) | Ciphertext | Tag(16B)` — ذخیره در یک ستون `varbinary` و `KeyId` در ستون/فیلد جداگانه با معنای «کدام کلید باید استفاده شود».
4. **Salt و پارامترهای KDF** همراه نسخه ثبت می‌شوند (`KeyMaterial` خارج از جداول داده؛ در Secret Store یا جدول اختصاصی با دسترسی محدود).
5. **رمز عبور کاربران هرگز با این کلیدها رمزنگاری نمی‌شود** — هش توسط Identity انجام می‌شود. (کلید ≠ هش)
6. **مولد کلید بی‌قاعده ممنوع:** هیچ «عبارت محرمانه به‌عنوان کلید AES» و هیچ «الگوریتم اختصاصی».
7. **هزینه محاسباتی PBKDF2** در محیط واقعی اندازه‌گیری و ثبت می‌شود (هدف: مجموع مشتق‌سازی MasterKey در راه‌اندازی، زیر ۲ ثانیه روی سرور هدف؛ پارامتر در `SecurityOptions`).
8. **رمزنگاری در راه‌اندازی یک‌بار** انجام و MasterKey در حافظه نگه داشته می‌شود (`IDataProtection` برای داده‌های غیرحیاتی مانند کوکی و Anti-forgery استفاده می‌شود؛ اما برای PII/رازهای بلندمدت استفاده **نمی‌شود** — چون چرخه کلید آن با نیاز «رمزنگاری مجدد داده» هم‌راستا نیست).

### ۴.۳ سرویس‌ها (قرارداد)
```csharp
public interface IKeyDerivationService
{
    DerivedKey DeriveMasterKey(ReadOnlySpan<char> passphrase, KeyDerivationParameters p);
    byte[] DeriveSubKey(DerivedKey masterKey, string purposeInfo, int lengthBytes); // HKDF
}

public interface ISecretProtector   // AES-256-GCM با قالب نسخه‌دار
{
    ProtectedPayload Protect(ReadOnlySpan<byte> plaintext, string purpose);
    byte[] Unprotect(ProtectedPayload payload, string purpose);   // Tag معتبر، در غیر این صورت Exception امن
}
```
- `KeyDerivationParameters`: `{ KdfId: "PBKDF2-SHA256", Iterations, SaltLength, Version, CreatedAtUtc }` — **ذخیره‌شده** تا مهاجرت‌های آینده ممکن باشد.
- هیچ سرویس دیگری نباید مستقیماً `AesGcm` بسازد؛ فقط `ISecretProtector`. (قاعده بررسی‌پذیر: جست‌وجوی کد `new AesGcm` فقط در یک فایل مجاز است.)

### ۴.۴ چرخه عمر کلید و بازیابی (نه فقط طراحی، بلکه رویه اجرایی)
| مرحله | رویه الزامی |
| --- | --- |
| ایجاد | تولید Passphrase تصادفی و قوی (حداقل ۲۵ کاراکتر) توسط مالک؛ ذخیره در Secret Store محیط + یک نسخه آفلاین رمزنگاری‌شده در گاوصندوق. **گم شدن Passphrase = غیرقابل بازیابی بودن داده‌ها.** |
| ثبت نسخه | جدول `KeyMaterial(KeyId, Version, SaltBase64, Iterations, KdfId, CreatedAtUtc, RetiredAtUtc?, Algorithm, Purpose)` — **بدون** Passphrase و بدون MasterKey |
| چرخش کلید (Rotate) | 1) KeyVersion جدید 2) `Protect` با کلید جدید برای رکوردهای جدید 3) Job رمزگذاری مجدد تدریجی (کلید قدیم فقط Decrypt) 4) پس از تأیید صحت، کلید قدیم `Retired` و فقط نگهداری پشتیبان 5) هرگز کلید قدیم تا پایان بازیابی داده‌ها حذف نمی‌شود |
| تغییر Passphrase | یک رویداد چرخش کلید است (نه تغییر سطحی)؛ آزمون روی کپی داده واقعی الزامی |
| پشتیبان‌گیری | Passphrase در پشتیبان دیتابیس **نیست**؛ باید مستقل و امن نگهداری شود. سند بازیابی گم‌شدن عبارت: `DEPLOYMENT.md` §Restore |
| آزمون | در فاز ۸ یک چرخش کامل کلید روی دیتابیس آزمایشی با رکوردهای واقعی‌نما اجرا و نتیجه ثبت می‌شود |

### ۴.۵ چه چیزی واقعاً رمزنگاری می‌شود؟ (تصمیم صریح)
| داده | رمزنگاری | دلیل |
| --- | --- | --- |
| کد OTP | هش (HMAC-SHA256 با `Key_OtpHmac`) — نه رمزنگاری | فقط نیاز به مقایسه؛ کد اصلی هرگز ذخیره نمی‌شود |
| کد ملی (در صورت نیاز محصول) | AES-GCM (`Key_Pii`) | قابل بازیابی برای نمایش به خود کاربر/اپراتور مجاز |
| API Key منابع نرخ و پیامک | AES-GCM (`Key_SecretStore`) | باید در زمان فراخوانی بازیابی شود |
| شماره موبایل | **بدون رمزنگاری ستونی** (نیاز به جست‌وجوی یکتا برای ورود) + ماسک در نمایش/لاگ | تصمیم: رمزنگاری قابل جست‌وجو، پیچیدگی و ریسک بالاتری از سود دارد. ریسک باقی‌مانده: دسترسی خواندنی به DB ⇒ دیدن شماره‌ها. کنترل: دسترسی محدود، پشتیبان رمزنگاری‌شده |
| رمز عبور | Identity Hash (PBKDF2) | استاندارد |
| تیکت/پیام محصول | بدون رمزنگاری | داده عملیاتی؛ محافظت با کنترل دسترسی |

## ۵. کنترل دسترسی (Authorization) — طراحی

**مدل:** نقش‌محور + مالکیت‌محور، همیشه سمت سرور.

```csharp
// Policyهای پیشنهادی (فاز ۱ و بعد)
"PublicAccess"            // فقط نمایش عمومی
"CustomerOnly"            // کاربر وارد‌شده + IsActive
"MemberFeatures"          // ماشین‌حساب تکمیلی/تاریخچه گسترده/علاقه‌مندی‌ها
"OperatorArea"            // Operator OR Admin
"AdminArea"               // Admin
"ManageUsersRoles"        // Admin — حساس
"ManageSystemSettings"    // Admin — حساس
"ManageSecrets"           // Admin + MFA + ثبت SecurityEvent — حساس
"ViewSecurityEvents"      // Admin
"ManageProducts"          // Operator OR Admin
"RespondToTickets"        // Operator OR Admin
"ViewOwnTicket"           // مالکیت در سرویس (نه فقط Policy) — دومین لایه دفاع
```
**قواعد اجرایی:**
- عملیات حساس (نقش‌ها، تنظیمات امنیتی، اسرار) به اپراتور داده نمی‌شود — **حتی با درخواست مستقیم**.
- هر کنترلر در `Areas/Admin` و `Areas/Operator` در سطح کلاس `[Authorize]` + Policy دقیق دارد.
- **تست ماتریس نقش×Endpoint** در فاز ۶ اجباری است (جدول خروجی در گزارش فاز).
- داشتن شناسه صحیح (ID/GUID) هرگز مجوز نیست؛ شرط مالکیت در همان کوئری دیتابیس اعمال می‌شود.

## ۶. حریم خصوصی داده
- حداقل‌سازی: فقط داده لازم ذخیره می‌شود (بدون کد ملی/آدرس بدون نیاز محصول).
- ماسک‌سازی در نمایش: شماره موبایل/ایمیل/آی‌پی در UI و لاگ ماسک یا هش می‌شوند.
- حق حذف: رویه ناشناس‌سازی در `DATA_MODEL.md` §4.
- داده حساس در `localStorage`/Cache سرویس‌ورکر ممنوع (فقط نرخ‌های عمومی).
- تهیه نمونه پشتیبان برای محیط تست فقط با داده ناشناس‌شده.

## ۷. پاسخ به رخداد (Incident Response) — حداقلی و عملی
1. **تشخیص:** هشدارهای `SecurityEvent` (تلاش ورود انبوه، خطای مکرر Provider، دسترسی رد شده زیاد).
2. **محدودسازی:** غیرفعال‌کردن حساب/منبع درگیر، چرخش کلید API، ابطال نشست‌ها (`SecurityStamp`).
3. **شواهد:** حفظ Log و Audit (بدون دست‌کاری)؛ ثبت زمان‌ها و CorrelationId.
4. **رفع و بازگشت:** اصلاح، اجرای تست رگرسیون، بازگردانی سرویس.
5. **گزارش:** ثبت در `docs/BUGS.md`/`CHANGELOG.md` + درس‌آموخته در `DECISIONS/` در صورت لزوم.
6. **آزمون:** پس از رخداد، Test جدید که همان سناریو را پوشش دهد (بدون استثنا).

## ۸.۱ اعتبارنامه سرویس نرخ — ریسک «Secret در URL» (فاز ۲)

قرارداد سرویس نرخ مالک، اعتبارنامه را در **مسیر آدرس** می‌گذارد: `https://.../Pr/Get/{username}/{password}`.
این یعنی اعتبارنامه در جاهایی که آدرس ثبت می‌شود دیده می‌شود: لاگ سرور، لاگ پروکسی، ابزارهای پایش، تاریخچه مرورگر و ابزارهای APM.

**کنترل‌های پیاده‌شده (اجراشده و تست‌شده):**

| کنترل | محل |
| --- | --- |
| آدرس واقعی هرگز لاگ/چاپ نمی‌شود؛ فقط قالب با `***` | `TgnEndpointTemplate.Describe` + تست‌های بازرسی لاگ (مسیر موفق و ناموفق) |
| عدم استفاده از `IHttpClientFactory` (که آدرس درخواست را در لاگ Information می‌نویسد) | `DependencyInjection.CreateRateHttpClient` |
| فقط `https` + دامنه محدود در فهرست مجاز (ضد SSRF) | `TgnEndpointTemplate.Validate` |
| سقف حجم پاسخ + مهلت درخواست | `TgnRateProvider` (`MaxResponseBytes`, `HttpTimeoutSeconds`) |
| اعتبارنامه فقط از ENV/User Secrets، هرگز در فایل/مخزن | `RateOptions.Username/Password` + پیام‌های راهنما با **نام** متغیر، بدون مقدار |
| پیام خطای سرویس (`{"Error":"Unauthorized"}`) تلخیص و کوتاه‌شده ثبت می‌شود (۳۲ نویسه) | `TgnRateProvider` |

**باقی‌مانده (پذیرفته‌شده):** اگر خودِ سرویس‌دهنده آدرس را در سیستم‌های خودش ثبت کند، از کنترل ما خارج است. توصیه: در محیط عملیاتی لاگ پروکسی/دیوار آتش برای این دامنه، بدنه و مسیر درخواست را ثبت **نکند** و در صورت امکان از IP اختصاصی با خروجی محدود استفاده شود.

## ۹. ریسک‌های پذیرفته‌شده و باقی‌مانده (به‌روزرسانی مستمر)
| ریسک | تصمیم | دلیل/جبران |
| --- | --- | --- |
| ممکن است عبارت محرمانه اشتباه تعریف شود ⇒ باگ در فرایند انسانی | پرچم‌گذاری در هر اجرای بدون داده‌های حساس + خطای صریح در Startup و تست سلامت کلید | جلوگیری از تولید داده رمزنگاری‌شده با کلید اشتباه |
| دسترسی خواندنی به DB ⇒ دیدن شماره تماس‌ها | پذیرفته‌شده | جبران با کنترل دسترسی سرور، پشتیبان رمزنگاری‌شده |
| وابستگی به API بیرونی و قطعی آن | پذیرفته‌شده (ذات محصول) | Cache + منبع جایگزین + نمایش صریح کهنگی |
| OTP در شبکه موبایل (SIM swap/رهگیری) | پذیرفته‌شده | MFA اختیاری برای مشتری در آینده؛ برای مدیران اولویت MFA |
| رفتار متفاوت PWA در iOS | پذیرفته‌شده | مستندسازی محدودیت‌ها و آزمون واقعی روی دستگاه |
