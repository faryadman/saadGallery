## ۱. خلاصه اجرایی

بیست سند دائمی، دو اسکریپت محیط و نُه ADR ساخته شد که دانش پروژه را از تاریخچه گفتگو مستقل می‌کند. معماری لایه‌ای ساده (MVC + EF Core + SQL Server + Identity)، مدل داده با دقت مالی صریح، مدل تهدید و طرح رمزنگاری مبتنی بر عبارت محرمانه (PBKDF2 + HKDF + AES-256-GCM + چرخش کلید)، و Roadmap فاز ۰ تا ۸ با معیار پذیرش **آزمون‌پذیر** تدوین شد.

**دو نکته صادقانه:**
1. **هیچ کدی نوشته نشده است** — طبق دستور شما، فاز صفر فقط بررسی و طرح است.
2. **منبع نرخ (API) هنوز به ما داده نشده** — بنابراین هیچ نرخ، نگاشت یا فرمولی بر مبنای حدس ساخته نشد. دقیقاً مشخص شده چه چیزی لازم است (`docs/API.md` §الف.۲ و `docs/OPEN_QUESTIONS.md` → `Q-API-1`).

### ۲.۴ بررسی اجمالی سرویس‌های نرخ (زمینه‌سازی، نه تعیین منبع)
نگاهی به بازار ایران انجام شد تا بدانیم **چه ساختارهایی رایج است** و کدام سؤالات را باید از شما بپرسیم. نمونه‌ها (فقط جهت شناخت؛ **هیچ‌کدام به‌عنوان منبع شما فرض نشده**): سرویس‌هایی با ساختار `{key, value, currency}` و `generated_at`؛ سرویس‌هایی با `title/value/change/quoted_at`؛ سرویس‌هایی با اعتبارسنجی `x-api-key` و محدودیت نرخ درخواست؛ الگوی رایج «حباب» به‌صورت عدد ارائه‌شده توسط خود سرویس (که ما آن را **نمی‌پذیریم** — محاسبه باید در کد ما و با فرمول نسخه‌بندی‌شده باشد).

> **مهم‌ترین یافته این بررسی:** در این بازار، **واحد اعداد (ریال/تومان)** و **معنای «زمان اعلام نرخ»** معمولاً مستند نیستند و شایع‌ترین منبع خطای ده‌برابری و نمایش داده کهنه به‌عنوان نرخ زنده همین دو مورد است. به همین دلیل این دو موضوع در طراحی ما «الزام صریح» شده‌اند (`ARC` §4، `API.md` §الف.۴، `ADR-0009`).

## ۴. تصمیم‌های کلیدی معماری (خلاصه + مرجع)

| موضوع | تصمیم | مرجع |
| --- | --- | --- |
| UI | MVC + Areas (Admin/Operator/Account)، RTL، Bootstrap 5.3.8 Self-host، بدون Blazor | ADR-0001 |
| دیتابیس | فقط SQL Server (بدون SQLite/InMemory در کد برنامه) | ADR-0002 |
| لایه داده | `DbContext` مستقیم در سرویس‌های Application؛ بدون Repository عمومی | ADR-0003 |
| هویت | Identity با کلید `int`، موبایل شناسه اصلی، OTP بدون رمز، قواعد ضد تصاحب حساب، MFA مدیران در فاز ۶ | ADR-0004 |
| نرخ | `IRateProvider` مستقل + DTO + Mapper تست‌شده + Fixture؛ تفکیک `QuotedAtUtc` از `FetchedAtUtc` | ADR-0005، ARC §5 |
| امنیت کلید | PBKDF2 (MasterKey) → HKDF (زیرکلید هر کاربرد) → AES-256-GCM؛ قالب نسخه‌دار؛ چرخش کلید | ADR-0006 |
| Job نرخ | BackgroundService + قفل دو‌لایه (SemaphoreSlim + قفل دیتابیسی) + Backoff | ADR-0007 |
| PWA | Manifest + Service Worker دست‌ساز با راهبرد کش صریح؛ **هرگز** کش صفحات احرازشده | ADR-0008 |
| پول/عیار | `Money(Amount, Unit)` و `Purity`/`Weight` نوعی؛ گرم واحد پایه؛ تبدیل فقط صریح | ADR-0009 |

### نکات امنیتی که مستقیماً به درخواست شما پاسخ می‌دهد
1. **عبارت محرمانه:** هرگز به‌عنوان کلید AES استفاده نمی‌شود؛ هرگز در سورس/Git/لاگ/پیام خطا نیست؛ از آن **فقط** برای مشتق‌سازی کلید استفاده می‌شود؛ بین کاربردها (PII / رازهای API / HMAC کد OTP / هش شناسه) **کلید مشترک وجود ندارد**؛ قالب داده نسخه‌دار و قابل ارتقا؛ **رویه چرخش کلید و آزمون بازیابی** طراحی شده؛ **گم شدن عبارت = غیرقابل بازیابی بودن داده رمزنگاری‌شده** و این ریسک صریحاً مستند شده است.
2. **رمز عبور کاربران با کلید پروژه رمزنگاری نمی‌شود** — هش استاندارد Identity.
3. **تصمیم صریح درباره اینکه چه چیزی رمزنگاری شود** (و چه چیزی نشود) در `SECURITY.md` §4.5 و `ADR-0006` آمده است.
4. **داشتن GUID مجوز نیست** — مالکیت در کوئری دیتابیس شرط می‌شود؛ تست IDOR در معیار پذیرش فاز ۵ اجباری است.
5. **کنترل دسترسی سمت سرور** با Policy؛ «پنهان‌کردن دکمه» به‌عنوان کنترل امنیتی پذیرفته نمی‌شود.

## ۵. مدل تهدید اولیه (خلاصه — کامل در `SECURITY.md` §2)

| تهدید | نمونه سناریو | کنترل اصلی | معیار اثبات |
| --- | --- | --- | --- |
| افشای تیکت دیگران | تغییر شماره تیکت در URL | شرط مالکیت در کوئری + 404 | تست دوکاربری (فاز ۵) |
| سوءاستفاده از OTP | ارسال انبوه، Brute، Replay | CSPRNG + هش + TTL + سقف تلاش + Rate Limit + یک‌بارمصرف | ۴ تست امنیتی OTP (فاز ۱) |
| بالا بردن سطح دسترسی | Customer روی `/Admin` | Policy سمت سرور + ماتریس نقش×Endpoint | جدول انطباق ۱۰۰٪ (فاز ۶) |
| XSS در تیکت/محصول | `<script>` در متن | ذخیره متن ساده + رندر Encode + CSP | تست Payload (فاز ۳/۵) |
| XSS از طریق فایل آپلودی | SVG/HTML با اسکریپت | سفیدلیست فرمت + بررسی واقعی محتوا + `nosniff` | تست آپلود مسموم (فاز ۴) |
| SSRF از BaseUrl | `http://localhost` به‌جای دامنه منبع | Allowlist + بلاک IP خصوصی + بدون Redirect | تست URL داخلی (فاز ۲) |
| افشای Secret | کلید در لاگ/appsettings | Redaction + Secret Store + اسکن مخزن | بازبینی لاگ + `git log -p` (فاز ۱/۸) |
| نمایش نرخ کهنه به‌عنوان زنده | قطعی API و نمایش مقدار قبلی | سه‌سطحی بودن کیفیت نرخ + برچسب صریح + `IsTrusted=false` | تست قطعی شبیه‌سازی‌شده (فاز ۲) |
| خطای داده‌ای مالی | ریال/تومان، عیار ۱۸ و ۲۴ | نوع `Money`/`Purity`/`Weight` + تست‌های تبدیل | تست واحد واحد-محور (فاز ۳) |

**ریسک‌های پذیرفته‌شده (شفاف):** امنیت ۱۰۰٪ وجود ندارد؛ گم‌شدن Passphrase؛ SIM-Swap در OTP؛ رفتار محدود PWA در iOS؛ دسترسی خواندنی DB ⇒ دیدن شماره تماس‌ها. جبران هر مورد مستند شده است.

## ۸. قدم بعدی دقیق (پس از تأیید شما)

**فاز ۱ — کوچک‌ترین بخش قابل اجرا (Increment 1):**
1. ساخت `SadGallery.sln` + `Directory.Build.props` (`net10.0`, Nullable، `TreatWarningsAsErrors`) + `Directory.Packages.props` (نسخه‌های Pin شده).
2. ساخت چهار پروژه اصلی + دو پروژه تست با جهت وابستگی درست و صفر هشدار.
3. Identity با نقش‌های سه‌گانه (Seed ایدمپوتنت) + DbContext + **مهاجرت اولیه** + صفحه سلامت `/health` + صفحه خطای فارسی.
4. یک تست واحد و دو تست یکپارچه پایه (علامت‌گذاری `RequiresSqlServer`).
5. اجرای واقعی `dotnet build -warnaserror` و `dotnet test` در سندباکس + ثبت خروجی در گزارش (و صراحتاً: تست‌های DB اجرا نشد).

**پیش‌نیاز شروع فاز ۱:** فقط یک جمله تأیید از شما («فاز صفر تأیید است»). پاسخ‌های `Q-API-1` برای شروع فاز ۱ **لازم نیست**، اما برای فاز ۲ **ضروری** است.
