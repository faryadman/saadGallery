## 🔴 مسدودکننده (بدون این‌ها فاز ۲ و بخشی از فاز ۱ قابل تکمیل نیست)

### Q-API-1 — منبع نرخ طلا و مسکوکات *(مسدودکننده فاز ۲)*
لطفاً موارد زیر را ارائه کنید (چک‌لیست کامل در `docs/API.md` §الف.۲):
1. **نمونه JSON واقعی** پاسخ موفق (متن کامل، بدون ماسک) — حتی اعداد واقعی روز.
2. Base URL و متد، و روش احراز هویت (نام دقیق Header؟ Query param؟).
3. **واحد اعداد: ریال یا تومان؟** آیا در پاسخ واحد ذکر شده؟
4. فهرست «کلیدهای دارایی» پشتیبانی‌شده (گرم ۱۸؟ مثقال؟ سکه امامی/بهار/نیم/ربع/گرمی؟ اونس؟).
5. زمان اعلام نرخ: فیلد زمان دارد؟ فرمت آن چیست؟ آیا Timezone دارد؟
6. محدودیت نرخ درخواست (در دقیقه/روز) و رفتار در تجاوز.
7. شرایط استفاده و حق بازنشر عمومی داده (آیا می‌توانیم نرخ را روی سایت نمایش دهیم؟).
8. **نمونه JSON ارز** و **نمونه JSON رمزارز** (اگر Endpoint جداگانه است).
9. آیا Endpoint تاریخچه/آرشیو دارد؟ بازه چند روز؟
10. **حالت خطا:** در قطعی سرویس/کلید نامعتبر، چه پاسخ و کد وضعیتی برمی‌گردد؟ (برای نوشتن تست)

**تا زمان دریافت:** تنها کد `IRateProvider`، DTO نمونه و Fixture تستی نوشته می‌شود. هیچ نرخ واقعی در سیستم تولید نمی‌شود.

### Q-COIN-1 — تأیید مشخصات استاندارد مسکوکات (فاز ۳)

سامانه حباب‌سنج بر پایه مشخصات زیر کار می‌کند (از منابع عمومی متعدد با ارجاع به استاندارد بانک مرکزی؛ تأیید شما لازم است):

| سکه | وزن کل (گرم) | عیار |
| --- | --- | --- |
| تمام (امامی / طرح قدیم) | ۸٫۱۳۳ | ۹۰۰ در هزار |
| نیم | ۴٫۰۶۶۵ | ۹۰۰ |
| ربع | ۲٫۰۳۳۲۵ | ۹۰۰ |
| گرمی | ۱٫۰۱ | ۹۰۰ |

۱. آیا این مشخصات با استاندارد مورد قبول شما (بانک مرکزی) مطابقت دارد؟ (برخی منابع برای ربع سکه ۲٫۰۳۲۲۵ گرم گزارش می‌کنند.)
۲. آیا «هزینه ضرب» پیش‌فرضی برای حباب‌سنج تعریف کنیم (مثلاً مبلغ ثابت به تومان) یا همان صفر بماند؟
۳. آیا سکه‌های غیربانکی (مثلاً پارسیان با عیار ۷۵۰) هم باید در مقایسه حباب پیشرفته بیایند؟

### Q-API-2 — پرسش‌های تازه سرویس نرخ (پس از دریافت مستندات و پیاده‌سازی فاز ۲)

مستندات و نمونه پاسخ دریافت شد و نگاشت پیاده‌سازی شد. این پرسش‌ها باقی مانده‌اند و **هرکدام می‌تواند رفتار سامانه را تغییر دهد**:

1. **محدودیت نرخ درخواست**: حداکثر چند فراخوانی در دقیقه/روز مجاز است؟ در تجاوز چه اتفاقی می‌افتد (۴۲۹؟ قطع سرویس؟ شارژ اضافه؟). پیش‌فرض فعلی ما ۶۰ ثانیه است.
2. **حق بازنشر عمومی**: آیا نمایش این نرخ‌ها به کاربران سایت (صفحه عمومی) مجاز است؟ اگر مجاز نیست، نمایش باید فقط برای اعضای واردشده یا فقط در پنل اپراتور باشد.
3. **واحد `Pelatin` (پلاتین)**: تومان بر گرم است؟ دلار بر انس؟ نگاشت آن **تا دریافت پاسخ متوقف است** (فعلاً فقط به‌عنوان «کلید ناشناخته» ثبت می‌شود).
4. **IP مجاز سرور عملیاتی**: چه IPهایی باید نزد سرویس‌دهنده ثبت شوند؟ (دامنه `webservice.tgnsrv.ir` به IP مجاز محدود است و از بیرون ایران قابل دسترسی نیست — از سندباکس ایجنت هم پاسخ نداد.)
5. **مرزهای معقول قیمت**: برای نگهبان خطای واحد، بازه معقول هر دارایی را تأیید یا اصلاح کنید (فعلاً بازه‌های پهن مهندسی: مثلاً گرم ۱۸ بین ۱۰۰٬۰۰۰ و ۵۰۰٬۰۰۰٬۰۰۰ تومان). با مرزهای واقعی شما، خطای «ریال/تومان» در نخستین دریافت هم گرفته می‌شود.
6. **بخش رمزارز**: نمونه‌ای برای ارز دیجیتال نفرستادید؛ آیا Endpoint جداگانه دارد یا فعلاً حذف شود؟ (در UI فعلاً خبری از رمزارز نیست.)
7. **زمان اعلام نرخ**: `TimeRead` بدون Timezone است؛ ما آن را وقت رسمی ایران (+03:30) در نظر می‌گیریم. تأیید می‌کنید؟
8. **Endpoint تاریخچه**: سرویس آرشیو می‌دهد؟ (اگر بدهد، تاریخچه دیتابیس ما سریع‌تر پر می‌شود؛ فعلاً تاریخیچه فقط از فراخوانی‌های خودمان ساخته می‌شود.)
9. **تغییر قرارداد**: در صورت تغییر نام/تعداد کلیدها توسط سرویس‌دهنده، اطلاع‌رسانی می‌شود؟ (ما کلیدهای ناشناخته را در هر اجرا ثبت می‌کنیم تا زود متوجه شویم، اما اطلاع مستقیم بهتر است.)

### Q-ENV-1 — محیط استقرار *(مسدودکننده فاز ۸)*
1. سیستم‌عامل سرور: Windows (IIS) یا Linux (Nginx/Kestrel) یا Docker؟
2. نسخه SQL Server (Express / Standard / Developer / 2022 / 2025) و محل آن (همان سرور یا جدا)؟
3. دامنه نهایی سایت و اینکه گواهی TLS دارید یا باید تهیه شود؟
4. Secret Store موجود (مثلاً Azure Key Vault، AWS Secrets Manager، HashiCorp Vault) یا استفاده از Environment Variables؟
5. آیا امکان اجرای **Staging** (محیط آزمایشی) وجود دارد؟ (برای آزمون Migration و بازیابی بسیار مهم است)

## 🟠 مهم (خروجی محصول را تغییر می‌دهد)

### Q-CONTENT-1 — محصولات و سیاست قیمت
1. حدوداً چند محصول و چند دسته در ویترین دارید؟ (برای طراحی UI و صفحه‌بندی)
2. سیاست قیمت هر محصول کدام است: ثابت / محاسباتی بر مبنای نرخ روز (وزن × نرخ + اجرت + سود) / فقط استعلام؟
3. اگر «محاسباتی»: فرمول دقیق چیست؟ (اجرت: درصدی یا مقطوع؟ سود: چند درصد؟ مالیات/ارزش افزوده؟)
4. اطلاعات تماس، آدرس، ساعات کاری، لینک اینستاگرام و وب‌سایت رسمی — متن نهایی کدام است؟
5. لوگو و تصاویر برند را داری؟ (برای آیکون PWA و سربرگ سایت، در ابعاد `512×512` و `192×192`)

### Q-COIN-1 — فرمول حباب و وزن مسکوکات
1. فرمول مورد نظر شما برای حباب کدام است؟ (مثلاً: `حباب = قیمت بازار − (وزن × عیار/۰.۷۵ × نرخ گرم ۱۸)` یا بر مبنای نرخ **طلای خالص/۲۴** — نتیجه کاملاً متفاوت است!)
2. نرخ مرجع کدام است: گرم طلای ۱۸ عیار، مثقال آبشده، یا اونس جهانی × دلار؟
3. وزن استاندارد و عیار کدام مسکوک را برایتان محاسبه کنیم؟ (امامی، بهار آزادی، نیم، ربع، گرمی)
4. هزینه‌های مرتبط (مالیات، اجرت، کارمزد) در فرمول لحاظ شود؟

### Q-SMS-1 — سرویس پیامک *(مسدودکننده کامل OTP واقعی)*
1. ارائه‌دهنده کدام است: کاوه‌نگار / sms.ir / ملی‌پیام / سایر؟
2. آیا حساب و **الگوی تأییدشده (Pattern)** دارید؟ (در ایران، متن OTP نیازمند الگوی تأییدشده است)
3. خط ارسال (شماره فرستنده) مشخص است؟
4. اعتبار فعلی حساب چقدر است؟ (برای فهم محدودیت ارسال)
5. آیا پشتیبانی از **Webhook وضعیت تحویل** لازم است؟

### Q-AUTH-1 — سیاست ورود
1. ثبت‌نام با موبایل یا با ایمیل — کدام مقدم است؟ (پیشنهاد فنی: موبایل مقدم، ایمیل اختیاری)
2. تأیید شماره/ایمیل اجباری است یا اختیاری؟
3. آیا «ورود بدون رمز با OTP» را برای همه کاربران می‌خواهید یا فقط اگر رمز را فراموش کردند؟
4. آیا MFA برای مدیران الزامی شود؟ (توصیه جدی: بله)
5. حساب‌های ادمین چقدر خواهد بود؟ (۱ نفر یا چند نفر، برای طراحی کنترل‌های حداقل دسترسی)

## 🟡 مفید (می‌توانیم با پیش‌فرض معقول شروع کنیم و صریح مستند کنیم)

### Q-DATA-1 — داده و نگهداری
1. مدت نگهداری تاریخچه نرخ چقدر باشد؟ (پیش‌فرض پیشنهادی: ۹۰ روز داده ریز، سپس تجمیع ساعتی/روزانه)
2. آیا تاریخچه نرخ برای کاربر مهمان و عضو باید متفاوت باشد؟ (پیش‌فرض: مهمان ۲۴ ساعت، عضو ۳۰ روز)
3. سیاست حذف حساب کاربری در صورت درخواست مشتری چیست؟ (پیش‌فرض: ناشناس‌سازی)

### Q-DEVDB-1 — دقت فنی برای پیش‌نمایش در محیط ایجنت
می‌دانیم SQL Server در محیط سندباکس ایجنت **در دسترس نیست**. سؤال:
- آیا موافقید **فقط برای اجرای محلی و پیش‌نمایش** (Dev-only، غیر از Production) یک مسیر اختیاری با پایگاه‌داده سبک (SQLite) اضافه شود، با این قیدها: (۱) هرگز در Production فعال نشود، (۲) تفاوت رفتارها مستند شود، (۳) تست‌های رسمی همچنان روی SQL Server اجرا شوند؟
  - الف) بله، اضافه شود تا پیش‌نمایش سریع داشته باشم.
  - ب) خیر؛ فقط SQL Server. پیش‌نمایش با داده واقعی روی ماشین خودم انجام می‌دهم.

> **پیش‌فرض تا پاسخ:** گزینه (ب) — فقط SQL Server، مطابق اصل «یک پایگاه‌داده، رفتار واحد». هیچ انحراف محیطی وارد کد نمی‌شود.

### Q-REPO-1 — نام مخزن *(غیرمسدودکننده)*
مخزن رسمی روی GitHub با نام `saadGallery` ساخته شده، در حالی که نام فنی پروژه در کد و مستندات `SadGallery` است.
- **پیش‌فرض فعلی:** نام فنی کد `SadGallery` می‌ماند و آدرس مخزن بدون تغییر استفاده می‌شود؛ این تفاوت روی Build/Deploy اثری ندارد.
- اگر ترجیح می‌دهید یکسان شوند: تغییر نام مخزن در GitHub ساده است و لینک‌های قبلی به‌صورت خودکار ریدایرکت می‌شوند. (گزینه دیگر: تغییر نام فنی به `SaadGallery` — نیازمند تغییر همه namespaceها و پوشه‌ها، پیشنهاد نمی‌شود.)

### Q-TICKET-1 — فرایند پشتیبانی
1. چه کسی به تیکت‌ها پاسخ می‌دهد و چند اپراتور خواهید داشت؟
2. آیا «ارجاع تیکت» به اپراتور دیگر لازم است؟ (پیش‌فرض: بله، با ثبت Audit)
3. آیا SLA (زمان پاسخ هدف) لازم است؟ (پیش‌فرض: نمایش «زمان انتظار» بدون هشدار خودکار)
4. تیکت بسته‌شده اگر مشتری پاسخ بدهد، بازگشایی شود؟ (پیش‌فرض: بله، وضعیت `AwaitingCustomer → InReview`)
