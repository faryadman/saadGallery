# ADR-0018 — خواندن پیام و اعلان تیکت به تفکیک کاربر
- تاریخ: 2026-10-14
- وضعیت: پیاده و آزموده؛ بازبینی مالک باقی
- دامنه: رفع خطای فرم و افزودن نشان پیام جدید به درخواست مالک.

## تصمیم
- TicketMessageReads با کلید مرکب UserId/OperatorView/MessageId، زمان UTC و FKهای Restrict ساخته شد. خواندنِ یک اپراتور برای دیگران مستقل است؛ نمای مشتری و صف اپراتور برای حساب دارای هر دو نقش نیز مستقل‌اند.
- شمارش فقط پیام عمومی طرف مقابل، با AuthorUserId متفاوت است. پیام خود کاربر، وضعیت و یادداشت داخلی شمرده نمی‌شوند. مالکیت مشتری در query شمارش و INSERT خواندن کنترل می‌شود؛ actor و نقش از Claims/Policy سرور هستند.
- GET گفت‌وگو فقط شناسه پیام‌های همان snapshot رندر را ثبت می‌کند. به‌جای watermark زمان/آخرین ID، رسید دقیق هر پیام استفاده شد تا پیام هم‌زمان یا commit دیرهنگام خوانده‌شده فرض نشود. دریافت DTO برای preflight ارسال و خطای POST، عکس و polling هیچ خواندنی ثبت نمی‌کنند.
- INSERT پارامتری و set-based با OPENJSON، UPDLOCK/HOLDLOCK و کلید یکتا برای باز کردن هم‌زمان idempotent است؛ SQL Server execution strategy موجود برای خطای گذرا باقی است. پیام‌های درخواست دوباره از جهت/مالکیت/نویسنده در SQL بررسی می‌شوند.
- نشان منو تعداد کل پیام خوانده‌نشده است؛ نشان ردیف تعداد پیام همان تیکت. GET مجاز `/tickets/unread` فقط شمارش و ID تیکت‌های قابل‌مشاهده درخواست‌شده را می‌دهد (حداکثر 25 ID)، بدون بدنه/کاربر/یادداشت. مشتری نمی‌تواند operatorQueue=true را درخواست کند. پاسخ و صفحات تیکت NoStore هستند.
- polling هر 30 ثانیه فقط در تب فعال آنلاین؛ در خطای شبکه آخرین نشان حفظ می‌شود. صفحه خودکار reload نمی‌شود، برای حفظ متن و عکس‌های انتخاب‌شده. پیام تازه داخل گفت‌وگو دکمه نمایش دارد. بدون JavaScript نشان هنگام پیمایش بعدی به‌روز می‌شود.
- مولفه منو در نبود DB خطا را فقط با نوع Exception ثبت و نشان را موقتاً پنهان می‌کند تا صفحه‌های دیگر خراب نشوند؛ شمارش در هر request بین جایگاه‌های منو به اشتراک گذاشته می‌شود.

## هزینه و بازگشت
رسیدها به تعداد پیام‌های خوانده‌شده × کاربران مشاهده‌کننده رشد می‌کنند؛ پاک‌سازی/Retention هماهنگ با حذف داده تیکت در آینده لازم است. SLA یا Push/پیامک اضافه نشد. Down فقط رسیدها را حذف می‌کند و به پیام/عکس/تیکت کاری ندارد؛ پس از ارتقای دوباره پیام‌های طرف مقابل دوباره خوانده‌نشده محسوب می‌شوند. هنگام rollback باید کد قبلی همراه schema قبلی به‌کار رود.

## شاهد
دو تست SQL تازه، اعلان شخصی مشتری، جداسازی اپراتورها، snapshot قدیمی در مقابل پیام هم‌زمان، باز کردن موازی، preflight بدون خواندن، نویسنده/یادداشت غیرقابل‌شمارش و مالکیت را می‌سنجند. کل 559 تست بدون Skip موفق؛ مرورگر اعلان دوطرفه، حفظ پیش‌نویس، خطای 400/409 و موبایل/دسکتاپ موفق؛ SQL رفت/برگشت و اجرای مجدد idempotent در DB جدا با داده آزمایشی موفق شدند.
