# ADR-0003 — استفاده از DbContext بدون لایه Repository

- **وضعیت:** Accepted
- **تاریخ:** 2026-10-05

## زمینه
سند اصلی می‌گوید: «از Repository، CQRS، MediatR و سایر الگوها تنها زمانی استفاده کن که ارزش واقعی و مشخصی ایجاد کنند» و «از Abstraction غیرضروری اجتناب کن».

## تصمیم
در لایه `Infrastructure`، سرویس‌های Application مستقیماً از `SadGalleryDbContext` استفاده می‌کنند. لایه Repository/UnitOfWork عمومی ساخته **نمی‌شود**.

## دلیل
1. `DbContext` خودش Unit of Work + Repository + Change Tracker + قابلیت بنچمارک‌شده دارد؛ پوشاندن آن با واسط عمومی، کد را بیشتر و شبیه‌سازی رفتارهای EF (Include، Projection، Split Query، Concurrency) را سخت‌تر می‌کند.
2. سناریوها ساده و مشخص‌اند و تست‌پذیری موردنیاز از طریق تست‌های یکپارچه روی SQL Server تأمین می‌شود (نه Mock کردن Repository).
3. جداسازی منطق از EF از طریق **سرویس‌های Application** (نه Repository) انجام می‌شود؛ Controller همچنان به EF دسترسی ندارد.

## قاعده جبرانی (برای حفظ قابلیت نگهداری)
- کوئری‌های پیچیده در کلاس‌های `Query` اختصاصی همان ماژول (`Infrastructure/Queries/`) یا متدهای `IQueryable` الحاقی محدود می‌شوند، نه اینکه در Controller پراکنده شوند.
- منطق تصمیم‌گیری (چه چیزی مجاز است، چه چیزی نمایش داده شود) در `Application` است و با تست پوشش می‌یابد.

## پیامدها
- **مثبت:** کد کمتر، نگهداری آسان‌تر برای مالک، استفاده از امکانات کامل EF.
- **منفی:** وابستگی سرویس‌های Application به EF در سطح پیاده‌سازی (که با تعریف اینترفیس‌های اختصاصی سرویس‌ها، نه اینترفیس داده عمومی، مدیریت شده). اگر روزی تعویض پایگاه‌داده لازم شد، این ADR بازبینی می‌شود.

## جایگزین‌های بررسی‌شده
- **Repository عمومی + UnitOfWork:** سود مشخصی نداشت؛ هزینه ترجمه مدل و ازدست‌رفتن توانمندی EF.
- **CQRS با MediatR:** برای این مقیاس، سربار شناختی و پیچیدگی دیباگ بدون بازده.
